## 2. 원인 셋 — 전부 확인했습니다

### ① 스케줄이 아예 없었다

`/api/cron/apt-master-ingest` 가 **`vercel.json` 에 없습니다.** 관리자 콘솔에서
손으로 누를 때만 돌았습니다. 적재 로그의 실행 시각이 09:00·10:20·11:08 처럼
들쭉날쭉한 이유가 이것입니다.

### ② 시계로 고른 슬라이스가 절반을 영원히 건너뛴다

훑을 시군구를 이렇게 골랐습니다:

```
idx = floor(now / 12시간) % ceil(263 / 12)      // 22개 슬라이스
```

하루 한 번 **같은 시각**에 도는 크론에서는 이 값이 매일 **2씩** 올라갑니다.
그래서 짝수 슬라이스만 방문하고 **홀수 11개 — 약 132개 시군구는 영원히 안 돕니다.**

적재 로그가 그대로였습니다:

```
09-06 slice=0/22    09-07 slice=2/22    09-08 slice=4/22    09-09 slice=6/22
```

1년을 돌려도 방문하는 슬라이스는 `[0,2,4,…,20]` 열한 개뿐입니다
(단위테스트가 이 사실을 재현해 고정합니다).

### ③ HTTP 실패를 "빈 시군구"로 삼켰다

```ts
const res = await fetch(url);
if (!res.ok) return { items: [], totalCount: 0, mode: "mock" };   // ← 사유가 사라진다
```

호출 한도 초과(429)·서버 오류(5xx)가 **"이 시군구에는 단지가 없다"와 구별되지
않습니다.** 그래서 로그에 사유 없이 `빈 시군구=41110,41111,…` 만 남았습니다.

목록 호출에는 **간격이 0** 이었습니다(상세 경로에는 이미 60ms 가 있었는데도).
한 실행이 12시군구 × 최대 20페이지 = **최대 240회를 연속으로** 때립니다.
슬라이스 12곳이 **한꺼번에** 비는 실패 모양은 "데이터 없음"이 아니라 한도 초과에
훨씬 가깝습니다.

## 3. 고친 것

| 무엇 | 어떻게 |
|---|---|
| 스케줄 없음 | `vercel.json` 에 하루 3회(UTC 04·12·20) 추가 — 기존 01시 군집을 피함 |
| 절반을 건너뜀 | 시계 대신 **가장 오래 안 본 시군구부터**. 대장에 한 행도 없는 곳이 최우선 |
| 실패를 삼킴 | 적재 경로만 `strict` — HTTP 상태와 "호출 한도 초과"를 로그에 남김 |
| 연속 호출 | 페이지·시군구 사이 120ms 간격(상세 경로와 같은 이유) |

새 순서는 **커서 테이블이 필요 없습니다** — 데이터 자체가 커서입니다. 실패해서 안
채워진 시군구는 다음 실행에 다시 1순위가 되므로 **자기 치유**합니다. 신선도 조회가
실패하면 예전 시계 방식으로 떨어집니다(조회 실패를 빈 목록으로 바꾸면 크론이 아무
일도 안 하고 성공처럼 보입니다).

근거 뷰: `public.apt_master_sigungu_freshness` (service_role 전용 · 운영 정보).

**한 바퀴 예상**: 263곳 ÷ 12곳 = 22회. 하루 3회면 **약 7.3일**. 지금 46곳이 비어
있으므로 **첫 나흘 안에 빈 곳이 먼저 채워집니다**(오래된 순이라).
