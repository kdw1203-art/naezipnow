## 왜 이번엔 "표"인가

청구(10/20~22 · Pro 구독 제외)는 ISR 쓰기 48% · 오리진 전송 28% · 함수 CPU 10% 였다. 1087~1091 로 "얼마나 자주 다시 만드는가"는 줄였으니 이번엔
**한 번 만들 때 얼마나 큰가**를 롱테일 전체에서 쟀다(로컬 빌드 · 1088 기준 서버와 같은 데이터).

| 화면(쪽 수) | HTML 전체 | 그중 RSC(인라인 — `.rsc` 로 한 벌 더 저장) |
|---|---|---|
| 동 `/dong/[region]/[dong]`(1,155) | **318KB** | **163KB** — 단지 표 113줄이 줄당 1.4KB |
| 구간 `/tx/[region]/[kind]/[band]`(약 1,680) | 178KB | 87KB |
| 허브 `/tx`(1 · 사람이 가장 먼저 여는 실거래 입구) | **498KB** | 251KB — 지역 칸 249개 |
| 입주 물량 `/supply`(1) | **513KB** | 330KB — 1,362행을 통째로 클라이언트에(키 이름이 45%) |

원인은 하나다. 서버 컴포넌트가 그린 표 · 칸은 HTML 과 RSC **양쪽에 원소 트리 그대로** 실린다(수화용). 줄마다 200B 짜리 단지 주소가 두 벌이다.
클라이언트 컴포넌트는 RSC 에 **props 만** 실리므로, 긴 표를 "압축 행 → 클라이언트가 그린다"로 바꾸면 RSC 가 줄당 1.4KB → 100B 안팎이 된다.
첫 화면 HTML(SSR)은 그대로라 크롤러 · JS 없는 환경이 보는 것은 같다. 표기 함수(toLocaleString · formatKrwShort)와 주소 규칙(lib/seo/complex-slug —
complex-store 의 encodeComplexId 와 같은 base64url)은 서버와 같은 것을 쓰므로 수화 불일치가 없다.
