# 979 — 화면별 Web Vitals 가 엉뚱한 화면에 기록되던 것 (2026-09-08)

앞판(977·978)에 이어, 관리자 콘솔의 **성능 매트릭스와 CWV 경보가 읽던 숫자 자체가
틀려 있었다**는 것을 찾아 고쳤다. 코드 한 줄이 느려서가 아니라, **재는 방법**이 틀렸다.

---

## 1. 무엇이 이상했나

`/admin/perf` 7일 p75 와 소유자에게 간 `[HEALTH] seo.cwv_page` 경보가 이렇게 말했다.

| 화면 | CLS | 표본 | 흔들린 요소로 기록된 것 |
|---|---|---|---|
| `/auctions` | **1.374** | 1 | `#main-content` |
| `/map` | 평균 0.544 / 최대 1.093 | 6 | 바텀시트 `aside…rise-in` · 지도 위 유리판 |
| `/` | 최대 **1.000** | 130 | `#main-content` |

CLS 1.0 은 "화면 전체가 한 번 통째로 밀렸다" 는 뜻이다. 그런데 같은 화면을
모바일 390×844 · CPU 4배 감속 · 느린 4G 로 직접 재면 `/map` 은 **0.0000**,
`/` 는 0.0226 이었다. 재현이 안 되는 숫자는 둘 중 하나다 — 우리가 못 재고 있거나,
**그 숫자가 그 화면 것이 아니거나**.

## 2. 원인 — 재현했다

리포터(`app/components/WebVitalsReporter.tsx`)는 지표를 보낼 때의
`window.location.pathname` 을 그대로 실었다. 그런데

- **CLS·INP 는 문서 수명 전체를 누적**하는 지표이고, `web-vitals` 는 그 값을
  **페이지가 숨는 순간 한 번** 확정한다.
- 앱 라우터에서 화면을 옮기는 것은 **새 문서를 여는 게 아니다.**

그래서 한 방문에서 쌓인 값이 **마지막으로 머문 화면**의 것으로 기록된다.
헤드리스 크롬으로 그대로 재현했다(2026-09-08):

```
홈(/) 에서 CLS 0.0199 누적  →  링크로 /map 이동  →  페이지 숨김
→ 실제로 전송된 것:
   CLS value=0.02  path=/map  el=a.btn-primary.glow…rise-in-3
                        ↑                ↑
              머문 마지막 화면      홈에만 있는 요소
```

`/auctions` CLS 1.374(표본 1건) 는 "공매 화면이 무너졌다" 가 아니라
**"공매 화면에서 브라우저를 닫은 어떤 한 사람의 방문 전체 흔들림"** 이었다.
`ops.cwv_page_check` 도 같은 표를 읽어 경보를 냈으므로, 소유자가 받은 알림도 같은 값이다.

같은 이유로 LCP·FCP·TTFB 도 확정 시점의 경로에 달릴 수 있었다.

## 3. 무엇을 바꿨나

`metric.delta`(마지막 보고와의 차이 — 구글이 분석 도구에 합산용으로 쓰라고 안내하는 값)를
`reportAllChanges: true` 로 받아 **그 시점에 보고 있던 화면의 통**에 넣는다.
화면을 옮기거나 페이지가 숨을 때 통을 비워 보낸다.

| 지표 | 어느 화면에 다는가 | 단위(`web_vitals.scope`) |
|---|---|---|
| CLS | 흔들림이 **생긴** 화면 | `route` |
| INP | 값이 **나빠진** 시점의 화면 | `route` |
| LCP·FCP·TTFB | 문서가 **처음 연** 화면 | `doc` |
| CLS·INP (방문 전체) | 문서가 처음 연 화면 | `doc` |

- 화면별 값의 합 = 문서 전체 CLS (단위 테스트로 고정)
- 클라이언트 라우팅으로 옮겨 온 줄은 `nav_type = 'soft-nav'` — 문서를 새로 연 게 아님을 사실대로 적는다
- bfcache 복귀는 `back-forward-cache` 그대로 (그때는 지표를 다시 재는 게 맞다)

### 왜 문서 단위 줄도 같이 남기나

화면 단위로 쪼개면 **단위가 바뀐다**. 예전 한 줄(방문당)이 여러 줄(화면당)이 되므로,
같은 표를 주 단위로 집계하는 `public.capture_seo_field_perf_rum` 의 p75 가
**사이트가 좋아진 것도 아닌데 내려앉는다.** 구글 CrUX 가 재는 단위도 문서 하나다.
그래서 숨는 순간 문서 전체 값을 `scope='doc'` 한 줄로 따로 남기고,
주간 시계열은 `scope <> 'route'` 만 읽는다 — 옛 표본(NULL)과 단위가 같아 선이 이어진다.

## 4. 옛 표본은 어떻게 하나 — 지우지 않고, 제외한다

`web_vitals` 에 남은 **23,956건**(2026-09-09 이전)은 `scope IS NULL` 이다.
지우지 않는다(가산만 원칙). 대신 **화면별로 줄 세우는 곳에서만** 뺀다.

- `ops.cwv_page_check` — `scope='route'`(CLS·INP) + `scope='doc'`(LCP) 만 본다.
  적용 직후 실행 결과 **경보 0건**. 틀린 값으로 소유자를 깨우지 않는다.
  새 표본이 `p_min_n=20` 만큼 쌓이면 다시 말하기 시작한다.
- `/admin/perf` — 뺀 건수와 이유를 화면에 적는다. 조용히 빼면 표본이 왜 줄었는지
  아무도 모른다.
- `capture_seo_field_perf_rum`(주간 사이트 전체) — 단위가 같으므로 옛 표본을 그대로 쓴다.

## 5. 확인한 것

| 무엇 | 방법 | 결과 |
|---|---|---|
| 잘못된 귀속 재현 | 헤드리스 크롬, 홈→/map→숨김 | `CLS 0.02 path=/map` (홈 요소) |
| 고친 뒤 | 같은 절차 | `CLS 0.011 scope=route path=/` + `CLS 0 scope=route path=/map soft-nav` + `CLS 0.011 scope=doc path=/` |
| 장부 규칙 | 단위테스트 17건 | 전부 통과 |
| 마이그레이션 | `ops.cwv_page_check()` 실행 | 0건(옛 표본 제외됨) |
| 전체 게이트 | `npm run build` | 통과 (단위 450건) |

## 6. 아직 모르는 것 — 지어내지 않는다

**이번 판은 "무엇이 느린지"를 고친 게 아니라 "어디가 느린지 볼 수 있게" 고친 것이다.**
지금까지의 화면별 숫자로는 어느 화면을 손봐야 하는지 알 수 없었다.

측정에서 실제로 재현된 것만 적는다(모바일 390×844 · CPU 4배 · 느린 4G):

- `/` LCP 2,204ms — 범인 요소 `a.today-slide` (실사용 p75 3,164ms, n=92 와 일치)
- `/map` LCP 6,644ms (실사용 p75 3,192ms)
- `/analysis` 실사용 LCP p75 5,579ms — 범인은 네이버 지도 **타일 이미지**(`rld=569ms`)
- CLS 는 어느 화면에서도 재현되지 않았다 (`/map` 0.0000, `/` 0.0226 — 둘 다 good)

`/` LCP 가 폰트 스왑 때문이라는 가설은 **직접 재서 틀렸음을 확인했다** —
Pretendard 를 차단하고 재도 2,204ms → 2,564ms 로 나아지지 않았다. 그래서
폰트 쪽은 건드리지 않았다.

다음 판에서 손댈 화면은 **이 판의 수집이 일주일 쌓인 뒤** 정한다.

## 7. 979b — 스냅샷에도 "어떤 규칙으로 잰 것인가"를 적었다

`ops.cwv_page_snapshot` 에는 **고치기 전 규칙으로 뜬 스냅샷 171건**이 남아 있다.
`ops.cwv_lcp_regression_check`(매일 22:05, 소유자 메일까지 나가는 경보)는
"오늘 스냅샷 vs 7~15일 전 기준선"을 비교하므로, 그대로 두면 **일주일 뒤부터
새 규칙 값과 옛 규칙 값을 견주게 된다** — 아무 일도 없었는데 회귀 경보가 뜨거나,
반대로 진짜 회귀가 가려진다.

그래서 스냅샷마다 `basis` 를 적고, 회귀 판정은 같은 규칙끼리만 한다.

| basis | 뜻 |
|---|---|
| `scope-v979` | 화면 귀속 교정 후에 뜬 스냅샷 |
| `NULL` | 그 이전 171건 — 지우지 않고, 비교 대상에서만 뺀다 |

적용 후 `ops.cwv_page_check()` · `ops.cwv_lcp_regression_check()` 둘 다 실행해
경보 0건 · 오류 0건을 확인했다.

## 8. 앞판(977) 정정 — matview-warm 은 아직 성공하지 않았다

977 에서 `cron.matview-warm-daily` 의 VACUUM 목록에서 사라진 릴레이션
(`market_agg.complex_households_resolved`)을 빼는 수정을 넣었다. 그런데 그 마이그레이션은
**2026-09-08 23:00 UTC** 에 적용됐고, 그날 이 잡이 도는 시각은 **19:20 UTC** 였다.
즉 09-08 19:20 실행은 고치기 **전** 명령으로 돌았고, 예상대로 같은 오류로 실패했다.

```
2026-09-08 19:20  failed   ERROR: relation "market_agg.complex_households_resolved" does not exist
2026-09-07 19:20  failed   (같은 오류)
2026-09-06 19:20  succeeded VACUUM
```

고친 명령이 **처음 도는 것은 2026-09-09 19:20 UTC** 다. 그때까지는 경보가 계속 뜬다.
다만 "돌아 봐야 안다" 로 두지 않고, 지금 명령이 부르는 릴레이션 11개가 전부
존재하는지 카탈로그로 확인했다 — **11/11 존재**. 명령 자체는 이제 성공할 상태다.
