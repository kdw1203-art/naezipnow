## 1. /town 이 120초를 태운 이유 — 산수였다

### 먼저: 느린 질의가 아니었다

의심부터 걷어냈다. 운영 DB 에서 직접 재 봤다(상한 5초, `docs/ops/db-analysis-safety.md` 규칙대로).

| 표 | 행 수 |
|---|---|
| `board_posts` | 897 (community·공개 896) |
| `board_comments` | **0** |
| `inspection_notes` | 27 (공개 25) |

문제의 질의를 `EXPLAIN (ANALYZE, BUFFERS)` 로 재니 **2.032 ms**였다
(인덱스 `board_posts_board_type_idx` 사용, 댓글 LATERAL 은 0행). 인덱스도 이미
다 있었다. 그런데 `pg_stat_statements` 상 같은 질의의 **평균이 209 ms · 최대
7,953 ms**다. 100배 차이는 질의가 무거워서가 아니라 **기다려서** 생긴 것이다.

### 진짜 원인: 예산 산수가 안 맞았다

이 저장소는 이미 규칙을 알고 있었다(`lib/newui/supabase-read.ts` 주석, 2026-07-27):

> 한 페이지의 직렬 조회 수 × 총 예산 < 페이지 예산

그런데 **런타임 쪽에서 이 부등식이 깨져 있었다.**

- 읽기 한 건의 총 예산: **45초**
- Vercel 함수 상한: **120초** → 직렬 **두 건**이 한계
- `lib/newui/board-posts.ts` 의 조회는 실패하면 **세 번** 간다
  (댓글 카운트 포함 → 카운트 없이 → anon)

**45초 × 3 = 135초 > 120초.** DB 가 밀리는 순간 이 함수 하나가 페이지 예산을
통째로 넘겼다. 그래서 `Vercel Runtime Timeout Error: Task timed out after 120
seconds` 295건, 경로의 대부분이 `/town/*` 였다.

같은 부류의 실수를 2026-08-01 감사가 한 층 위에서 이미 고쳤다("시도별 상한만
있고 총 상한이 없다"). 층이 하나 더 있었던 것뿐이다.

### 고친 것

**(a) 세 시도가 함께 쓰는 벽시계 예산 12초** — `AbortSignal` 하나를 세 질의에
같이 물린다. `resilient-fetch` 는 넘겨받은 signal 이 끊기면 자기 재시도(503
백오프)도 멈추므로 전 구간이 한 번에 잘린다. 12초를 넘긴다는 건 질의가 무거워서가
아니라 연결을 못 잡고 있다는 뜻이고(위 2ms 실측), 그때는 빨리 물러나는 편이 낫다.
호출부(`/town/[region]`)는 이미 실패를 `postsFailed` 로 받아 화면에 적는다 —
흰 화면 120초보다 낫다.

**(b) 런타임 읽기 예산 45초 → 20초, 시도별 25초 → 10초.**
근거(실측): PostgREST 는 `authenticator` 세션의 `statement_timeout=8s` 로 이미
잘린다 — `pg_stat_statements` 상 어떤 질의도 max 7,9xx ms 를 못 넘는다. 즉 8초
넘게 기다리는 시간은 질의 시간이 아니라 **연결 풀 대기**다. 풀이 20초 넘게 안
비면 그 요청은 이미 죽은 요청이고, 붙들고 있을수록 풀이 더 마른다.
20초면 부등식이 **직렬 6건**까지 성립한다.

**(c) 그 산수를 사람 주석이 아니라 숫자로 잠갔다.**
`lib/supabase/read-budget.ts` 신설 — 두 클라이언트가 같은 상수를 쓰고,
`tests/unit/read-budget-976.test.ts` 가 부등식을 검증한다. 예전 45초 값이
직렬 3건에서 깨진다는 사실도 회귀 테스트로 박아 뒀다.

## 2. 폴백이 같은 DB 에 기대고 있었다

967 에서 공개 임장노트에 "마지막 정상본" 폴백을 붙였는데도 오류가 그대로
남았다(최근 7일 477건 · 189명, 오늘 새 배포에서도 7건). 이유는 단순하다 —
그 폴백이 읽는 `public_data_cache` 가 **같은 Postgres** 다. 폴백이 필요한
순간은 DB 가 밀렸을 때이고, 그때는 폴백도 같은 풀에서 같이 죽는다.

층을 하나 앞에 뒀다: **이 인스턴스가 직접 성공했던 값**을 메모리에 들고 있다가
먼저 낸다(`lib/cache/memory-last-good.ts`). 왕복 0회라 포화 상태에서도 확실히
뜨고, 자기가 읽어 본 적 없는 값은 절대 내지 않는다. 인스턴스가 식으면 사라지는데
그건 결함이 아니라 이 층의 성격이다 — 식은 인스턴스는 예전 길로 내려간다.

    ① 메모리 정상본(24시간) → ② DB 정상본(24시간) → ③ 실패를 던짐

낡은 값을 방금 값처럼 내지 않는 규칙은 그대로다(`stale: true` 로 표시).
모두에게 같은 공개 목록에만 쓴다 — 사용자별 값은 인스턴스가 재사용되므로
이 층에 올리지 않는다(모듈 주석에 못 박아 뒀다).

## 3. 다크 모드 — 흰 글자를 얹는 파랑 면만 골라서

975 에서 "앱 전체 버튼 색이 바뀌는 변경이라 지시 없이 하지 않는다"고 남긴
항목이다. 이번 지시로 처리했다.

문제는 `--primary` 가 다크에서 **밝은 파랑(#5b8bff)** 으로 뒤집힌다는 데 있다.
어두운 면 위 *글자* 로 읽히려면 그래야 하는데, 같은 값을 **면**으로 쓰고 흰 글자를
얹으면 3.18~3.21:1 이 된다.

마크업 57곳을 고치는 대신 **문제가 되는 조합만** 선택자로 집었다.

```css
.dark .bg-primary.text-white,   /* 파랑 면 + 흰 글자 */
.dark .btn-primary,             /* 클래스가 스스로 color:#fff */
.dark .ai-chip { background: var(--primary-fill); color: #fff; }
```

장식용 `bg-primary`(강조 바·점 등, 글자가 없다)는 건드리지 않았다 — 거기서는
밝은 파랑이 어두운 면 위에서 더 잘 보인다. 라이트 모드도 그대로다(이미 6.64:1).

테마 4종에 `--primary-fill` 을 뒀고, 대비 게이트가 **흰 글자 AA + 표면과 3:1 분리**를
라이트·다크 양쪽에서 검사한다. `/qna` 청록은 그 검사에서 걸려(다크 표면 대비 2.94)
채움만 한 톤 밝은 `#0c7d74` 로 갈랐다(5.00 / 3.45).

### 그 과정에서 나온 곁가지 세 개 (전부 실측으로 걸림)

| 자리 | 무엇이 문제였나 | 후 |
|---|---|---|
| `/dev-deals` 등록 버튼 | 인라인 `style={{color:"#fff"}}` — 색을 인라인으로 박으면 위 다크 규칙이 이 자리를 못 집는다 | `text-white` 클래스로 (2.93 → 통과) |
| `/dev-deals` 안내 칩 | `bg-white/70` 은 라이트 전제 값. 다크에서 배너 글자색(밝은 앰버)이 흰 칩 위 **1.14:1** | `bg-surface` |
| 헤더 아바타 동그라미 | `from-line→to-line-strong` 그라데이션 중간색 위 4.41:1. 모든 화면 헤더에 있다 | `bg-primary-soft`(게이트가 보증하는 짝) |

### 그리고 조용히 안 먹던 클래스 하나

탭바 활성 라벨("기록")을 `text-primary-strong` 으로 바꿨는데 색이 안 변했다.
`--color-primary-strong` 이 Tailwind 토큰으로 **등록돼 있지 않아서** 그 유틸리티가
아예 없었던 것이다. 클래스를 붙여도 조용히 무시된다. 토큰을 등록하고 다시 재니
4.41 → **5.67**. (탭바는 유리라 뒤 배경이 비쳐, 본문이 어두운 화면에서 실제
바탕이 #ced3da 까지 내려간다.)

### 측정에서 알아 둘 것 — 로컬 검증의 함정 하나 더

`rm -rf .next` 후 새로 빌드했는데도 `/dev-deals` 의 prerender HTML 이 **옛 마크업**

해당 `.html`/`.rsc`/`.meta` 를 지우고 서버를 다시 띄우자 새 마크업이 나왔다.
원인은 확정하지 못했다 — 지어내지 않고 사실만 적는다. **화면으로 검증할 때는
빌드 산출물의 prerender HTML 이 실제로 갱신됐는지 한 번 확인할 것.**
(972·974 에 적은 "로컬 .next 재사용" 함정의 변종으로 보인다.)

또 하나: 등장 애니메이션(`rise-in`·`data-reveal`)이 끝나기 전에 재면 대비가
중간 opacity 로 잡혀 **오탐 47건**이 나온다. 측정 스크립트는 `reducedMotion`
+ 4초 대기 + `data-reveal="shown"` 강제 후에 잰다.

### 5-1. DB 부하의 진짜 상위 항목 (35일 누적, `pg_stat_statements`)

이번에 고친 건 "밀렸을 때 죽지 않게" 하는 쪽이다. **왜 미는가**는 아직 남았다.

| 질의 | 호출 | 누적 | 평균 | 최대 |
|---|---|---|---|---|
| `region_rent_yield_summary(p_months)` RPC | 157,618 | **4.02시간** | 92ms | 7.9초 |
| `market_transactions` 계열 4종 | 1,045,359 | 7.6시간 | 9~89ms | 8.0초 |
| **`ops.refresh_market_aggregates_cron()`** | 42 | 1.65시간 | **141초** | **12.4분** |
| `board_posts` 계열 3종 | 652,400 | 2.6시간 | 8~209ms | 8.0초 |
| `apartment_complexes` | 382,458 | 1.3시간 | 12ms | 7.7초 |
| `apartment_supply` | 489,500 | 1.19시간 | 9ms | 0.9초 |
| `capture_data_quality_snapshot()` | 37 | 0.54시간 | **52초** | 4.2분 |

읽히는 그림은 둘이다.

1. **호출 수 자체가 많다** — 35일에 약 270만 건, 하루 7.7만 건(초당 0.9). Micro
   인스턴스에 상시로 얹히는 부하다. 화면 한 장이 조회를 몇 건 내는지부터 봐야 한다.
2. **야간 크론이 몇 분씩 인스턴스를 통째로 먹는다** — `market-aggregates-daily`
   (19:00 UTC = 04:00 KST)가 최대 12.4분. 한국 새벽이라 사용자 영향은 작지만,
   그 시간대에 걸린 요청은 전부 죽는다.

`region_rent_yield_summary` 는 2026-08-25 에 6시간 캐시를 붙였다. 위 157,618건은
**캐시 이전 3주가 대부분**으로 보이지만(창이 8/4~9/8), 지금 값만 따로 보려면
`pg_stat_statements_reset()` 이 필요하다 — 과거 기록이 사라지므로 지시 없이
하지 않았다.
