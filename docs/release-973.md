## 원인 — 제가 냈습니다

같은 시각에 저는 971 작업으로 **분석용 대용량 질의**를 운영 DB 에 돌리고 있었습니다.
상한을 걸지 않았습니다. `pg_stat_statements` 실측:

| 질의 | 총 실행시간 |
|---|---|
| 필지 매칭 측정(실거래 33,182 × 대장 22,155, `regexp_match` 조인) | **29,536 ms** |
| 같은 계열 측정 | 11,411 ms |
| `create materialized view complex_master_link` | 7,850 ms |
| `refresh materialized view concurrently` ×3 | 6,600 ms |

Micro 인스턴스에서 30초짜리 전체 스캔은 다른 모든 질의를 밀어냅니다. 그래서 평시
**15.8ms** 인 단지 대표행 조회가 6초 상한을 넘겼고, PostgREST 는 503 을 돌려줬습니다.

경보의 "외부 API 오류는 감지되지 않았으므로 서비스 내부 문제" 라는 자동 진단은
반은 맞았습니다 — 상위 API(국토부 등)는 멀쩡했고, 문제는 우리 DB 였습니다.

## 그런데 코드가 사고를 **키웠습니다**

포화는 몇 초면 지나가는데 오류가 한 시간 갔습니다. 코드에 증폭기가 셋 있었습니다.

1. **상한이 질의를 취소하지 않았다.** `Promise.race` 는 약속만 버립니다 — HTTP
   요청도, 그 뒤의 Postgres 질의도 계속 살아 있었습니다.
2. **그 위에 350ms 뒤 재시도가 하나를 더 얹었다.** 요청 하나가 살아 있는 질의 둘.
3. **상한 없는 쓰기용 클라이언트로 조회하고 있었다.** 그래서 시도별 상한도,
   PostgREST 503 백오프 재시도도 없었습니다(읽기 전용 클라이언트에는 둘 다 있습니다).

즉 포화가 시작되면 트래픽이 포화를 스스로 키우는 구조였습니다.

## 고친 것

| # | 바뀐 것 | 파일 |
|---|---|---|
| 1 | 대표행 조회를 **읽기 전용 클라이언트**로 — 시도별 상한·총 예산·502/503/504 백오프 재시도가 붙는다. anon 폴백도 안전(market_transactions 는 anon SELECT 열림, 실측) | `lib/complex/complex-store.ts` |
| 2 | 상한이 끝나면 **AbortSignal 로 질의를 끊는다** — 대표행·대장 보강 모두 | `complex-store.ts` · `app/complex/[id]/page.tsx` |
| 3 | 대표행 상한 **10초 → 4초**(평시의 250배). 10초는 평시의 600배였고, 그만큼 기다린다고 답이 오지 않는다 | `page.tsx` |
| 4 | 시간 초과가 **창(20초) 안에서 연속 3회**면 재시도를 끈다. 성공 한 번이면 즉시 복귀 | `lib/db/timeout-breaker.ts` (신설) |
| 5 | 대장 보강(세대수·난방 등)에 **2.5초 상한** — 예전엔 상한이 아예 없어서 함수 상한(300초)까지 붙잡힐 수 있었다. 넘기면 던지지 않고 실거래만으로 그린다 | `page.tsx` |

**바꾸지 않은 것**: 시간 초과는 여전히 `throw` 입니다. 200 으로 "일시 오류" 화면을
돌려주면 ISR 이 그걸 6시간 캐시하고, `null` 을 돌려주면 `notFound()` 가 "조회 실패"를
"없는 단지(404)"로 위장합니다. 둘 다 지금보다 나쁩니다. 실패 화면은 이미 한국어
에러 바운더리(`app/error.tsx` — 다시 시도·홈·문의)가 그립니다.

## 재발 방지 (제 쪽)

`docs/ops/db-analysis-safety.md` 를 새로 썼습니다. 세션이 바뀌면 제 기억은 사라지지만
저장소는 남으므로, 규칙을 거기 적어 뒀습니다.

- 탐색·측정 질의는 `set local statement_timeout = '5s'` 를 붙여서 던진다.
  상한에 걸리면 그 자체가 답이다("이 방식은 운영에서 못 쓴다").
- 표본으로 먼저 재고 전수는 마지막 한 번. 971 에서 전수 측정을 네 번 돌렸는데
  셋은 표본으로 충분했다.
- 매트뷰 생성·`REFRESH CONCURRENTLY` 는 트래픽이 적은 시간에.
- 무거운 걸 돌린 뒤에는 `pg_stat_statements` 로 영향을 확인한다.
